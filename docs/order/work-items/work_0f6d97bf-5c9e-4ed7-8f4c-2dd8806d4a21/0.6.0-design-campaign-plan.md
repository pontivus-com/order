## 1. Purpose

This document governs the complete Order 0.6.0 design campaign from prerequisite investigation through an adversarially reviewable implementation plan.

The campaign is intentionally concern-driven rather than screen-driven or implementation-driven. Its primary objective is to reconstruct, from canonical P2/P3 authority, the complete intended functional design that the 0.5.0 work was supposed to realize; then derive the 0.6.0 technical solution design and implementation plan that will actually realize that design. The released 0.5.0 application, its tests and its rendered UI are evidence only and never define what 0.6.0 must preserve. The campaign makes omissions visible by ensuring that every material product concern has an explicit investigation start, an explicit factual end, a functional-design disposition, a technical-design disposition and final implementation-plan coverage.

The campaign progression is:

```text
G0 — Phase 0 factual/governance baseline established
  |
  v
PHASE 1 / R1
complete concern inventory + evidence-first concern investigations
  |
  | G1/G2: coverage proven; every investigation factually closed
  v
PHASE 2A / R2
complete 0.6.0 functional requirements / functional design
  |
  | G3: all concerns functionally closed + horizontal integration PASS
  v
PHASE 2B / DESIGN
complete technical solution design / P4-P6 consequences
  |
  | G4: all functional obligations technically realized
  v
PHASE 3 / PLAN
final executable implementation plan
  |
  | G5: complete P1->P7 traceability, no orphan task or uncovered requirement
  v
PHASE 4 / R3
adversarial readiness review
  |
  | G6: READY_FOR_SIGNOFF
  v
explicit sign-off / implementation authority
```

Actual implementation is outside this campaign plan. It begins only after the canonical PLAN and R3 package has been explicitly signed off.

## 4. No current-state fallback / no regression-baseline rule

The 0.6.0 campaign is an authority-driven design campaign. **Current application state, current UI composition, current implementation behavior and current design shape are not campaign outputs and are never a fallback definition of desired behavior.**

Current code, tests, rendered UI, historical design documents and prior releases may be inspected only as transient evidence to:

- prove a defect or contradiction against canonical authority;
- identify an existing capability that a later DESIGN decision may deliberately reuse;
- locate an ownership/boundary failure;
- determine migration/deletion consequences after the required future behavior is already established;
- prove that a claimed correction actually landed.

They must **not** be copied into this plan, `research.md`, `requirements.md`, `solution-design.md` or another campaign artifact as a descriptive inventory of "how the application currently works", a preservation baseline, compatibility target, regression contract, fallback behavior or implicit requirement.

The governing direction is always:

```text
canonical product intent / authority
        -> factual gap or unresolved decision
        -> required 0.6.0 behavior
        -> technical realization
        -> implementation plan
```

and never:

```text
current application/design state
        -> preserve by default
        -> document as desired behavior
```

A concern investigation therefore records only:

1. applicable canonical authority and accepted intent;
2. contradictions, missing decisions, ownership defects or unproven obligations;
3. exact decision inputs required by R2/DESIGN;
4. cross-concern dependencies;
5. verification evidence sufficient to support the finding.

Implementation observations remain cited evidence behind a finding; they are not restated as product facts unless the same statement is independently owned by canonical authority. Absence of a finding does not mean "keep the current application"; it means the existing canonical authority is sufficient for that concern.

Any wording such as "preserve current", "keep existing", "match current", "unchanged behavior", "current design is correct", or equivalent is invalid unless it refers to an explicitly cited canonical semantic obligation rather than incidental implementation/design state.

### 4.1 Campaign-purpose precedence

The purpose of this campaign outranks transient evidence and delivery status. A PR/CI result, browser test, existing regression, current implementation behavior, historical design statement, concern status note or handover may not become a functional requirement, preservation contract or campaign gate by implication. Such evidence may stop the campaign only when it proves that the canonical authority, document-authoring contract or conformance machinery needed to reconstruct R1/R2/DESIGN/PLAN is itself defective. Otherwise it is routed to the appropriate later design, implementation or delivery work and the authority-driven reconstruction continues.

Browser/UI tests become relevant to 0.6.0 acceptance only after reconstructed functional requirements and technical design establish the behavior they must verify. Existing browser tests do not constrain the reconstructed design merely because they describe or protect 0.5.0 behavior.

## 8. Concern investigation protocol

Every concern uses the same explicit START -> investigation -> END protocol.

### 8.1 START record

Before evidence collection for a concern begins, add a START record to the concern log in this document:

```text
CONCERN START: Cxx — <name>

Start baseline:
- exact repository commit:
- date:
- current phase: R1

Canonical owners:
- ...

Requirement families:
- ...

Upstream intent:
- ...

Known downstream consumers:
- ...

Incoming cross-concern findings:
- ...

In scope:
- ...

Explicitly out of scope:
- ...

Questions to close:
1. What does canonical authority require for this concern?
2. Is that authority complete and internally consistent for 0.6.0?
3. What exact gaps or decisions remain before future behavior is unambiguous?
4. Which adjacent concerns can invalidate this concern's closure?
```

A concern is then changed from `NOT_STARTED` to `IN_REVIEW`.

### 8.2 Mandatory R1 analysis dimensions

Each concern investigation must close:

1. **Intent** — canonical P2/product reason and required user outcome.
2. **Authority** — canonical owner(s), stable requirement identities and applicable higher rules.
3. **Authority completeness** — contradictions, missing decisions, ambiguous ownership or unproven obligations that prevent a complete 0.6.0 decision.
4. **Information ownership** — required canonical source facts and semantic producer -> carrier -> consumer ownership where the authority depends on them.
5. **Interaction obligations** — only the operator-visible behavior required or left undecided by canonical authority.
6. **State/transition closure** — required lifecycle/material/proposal/approval/task/provider semantics and any missing decision.
7. **Negative behavior** — prohibited behavior and failure semantics owned by authority.
8. **Recovery obligations** — blocker, retry, stale, cancellation and return-to-owner requirements.
9. **Cross-concern interfaces** — authority/decision dependencies imported from or exported to other Cxx concerns.
10. **Proof state** — evidence sufficient to prove a finding or closure, without turning observed implementation/design state into a campaign-owned baseline.

Current code, tests, UI and prior design may be inspected to prove a finding, but their incidental shape is never recorded as desired behavior, preservation scope or fallback semantics.

### 8.3 END record

A concern investigation cannot stop informally. It ends with:

```text
CONCERN END: Cxx — <name>

End baseline:
- exact repository commit:
- date:

R1 verdict:
VERIFIED | GAP_FOUND | BLOCKED

Authority facts / decision inputs established:
- ...

Findings:
- Cxx-F01 ...
- ...

Cross-concern findings emitted:
- X-Cxx-Cyy-01 ...
- ...

Incoming findings resolved:
- ...

Canonical owners implicated:
- ...

Open product decisions for R2:
- NONE | ...

Open factual questions:
- NONE | ...

R1 disposition:
FACTS_CLOSED | GAP_FOUND | BLOCKED

Revalidation trigger:
- ...
```

`VERIFIED` means the factual model is closed; it does **not** mean no 0.6.0 functional change is needed.

No concern reaches R2 while it has an unresolved factual question that could materially change the functional decision.

## 9. Finding and dependency discipline

### 9.1 Stable finding identities

Use:

- `Cxx-Fnn` — finding owned by one concern;
- `X-Cxx-Cyy-nn` — finding discovered in Cxx but requiring disposition in Cyy;
- `G-Fnn` — genuinely campaign-wide foundational finding.

A finding is recorded once at its primary owner and referenced elsewhere.

### 9.2 Cross-concern rule

When C06 exposes a problem in C11, C06 records `X-C06-C11-nn`; C06 does not redesign Approval while still investigating Research.

The C11 START record must list that incoming finding. C11 cannot close until it has explicitly disposed it.

### 9.3 Foundational defect rule

If an investigation exposes a Phase 0-class problem—ambiguous canonical ownership, broken reference lineage, shadow authority, impossible lifecycle topology, or another foundation defect—the active concern becomes `BLOCKED`.

The defect is remediated at its canonical owner through a separately governed WorkItem. After that remediation lands, all concerns whose evidence/authority depended on the changed foundation enter `REVALIDATION`.
