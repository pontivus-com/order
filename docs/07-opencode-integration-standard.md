# 07 — OpenCode integration standard

**Status:** Binding design standard
**Canonical concern ID:** `GW-DOC-OPENCODE-INTEGRATION`  
**Versioned concern ID:** `GW-DOC-OPENCODE-INTEGRATION-V1`  

## 1. Purpose

OpenCode is an execution provider inside Order. It is not the workflow engine, task database, approval authority, retry controller, canonical project context, or completion authority.

Order manages OpenCode through one narrow V2 server/client shell whose behavior is capability-certified before productive work.

## 2. Verified v1 provider baseline

The exact v1 OpenCode server/client pins and their provenance are owned exclusively by [GW-DOC-EXTERNAL-FACTS-V1-2026-11-12](14-external-version-facts.md). This document owns only the integration semantics for that bound provider/client pair:

- OpenCode server binary: exact pin from `GW-DOC-EXTERNAL-FACTS-V1-2026-11-12`;
- V2 TypeScript client: matching exact pin from `GW-DOC-EXTERNAL-FACTS-V1-2026-11-12`;
- HTTP API: released OpenCode V2 server API;
- server process: Order-owned foreground `opencode serve`;
- network: loopback only;
- server authentication: V2 `OPENCODE_PASSWORD`, username `opencode`.

The server binary and client package must have the same exact version. Order checks the binary version and authenticated `GET /api/info` (`client.server.info()`) before using the provider and rejects a version mismatch. "Latest OpenCode" is never an admissible runtime configuration; the exact audited version is.

Order does not use the OpenCode shared/background service and does not depend on repeated `opencode run --session` process invocations for interaction.

The plain foreground launch mode is material. In the OpenCode build bound by `GW-DOC-EXTERNAL-FACTS-V1-2026-11-12`, restart continuity is installed only when the server is started with a lifecycle hook; the CLI supplies that hook for `opencode serve --service`, not for plain foreground `opencode serve`. Order v1 therefore does not rely on OpenCode automatic suspended-session restart recovery. Switching Order to `--service` is a P4/P6 integration change, not an implementation detail.

The behavioral contracts in §§7–8 are grounded in the pinned OpenCode `v2.2.6` sources: `specs/v2/session.md`, `packages/protocol/src/groups/session.ts`, `packages/schema/src/session.ts`, `packages/schema/src/session-message.ts`, `packages/core/src/session/session.ts`, `packages/core/src/session/projector.ts`, `packages/core/src/session/runner/llm.ts`, `packages/cli/src/server-process.ts`, `packages/server/src/process.ts` and `packages/protocol/src/groups/event.ts`.

## 3. Provider process isolation

Order starts the pinned OpenCode server as its own child process with an explicit allowlisted environment. It does not inherit the user's provider configuration surface.

The exact v1 launch is:

```text
opencode serve --hostname 127.0.0.1 --port 0
```

Port `0` delegates private-loopback port allocation atomically to the OS. Order reads bounded provider stdout until the bound foreground server reports `server listening on http://127.0.0.1:<port>`, rejects any non-loopback/malformed result, and then performs the authenticated exact-version readiness/identity probe through `GET /api/info` (`client.server.info()`). Startup has a fixed 60-second bound.

The child receives:

- one per-provider-process `OPENCODE_PASSWORD` generated by [GW-DOC-CANONICAL-CONTRACTS-V1 §3](13-canonical-contracts.md);
- private `HOME=<order-state>/opencode/home`;
- dedicated `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `XDG_CACHE_HOME` and `OPENCODE_DB` below Order state;
- `OPENCODE_DISABLE_PROJECT_CONFIG=1`;
- `OPENCODE_DISABLE_CLAUDE_CODE=1`;
- `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1`;
- the embedded OpenCode web UI is not a Order surface: the provider remains on its private random loopback port, Order never exposes or forwards that port or UI, and Order consumes only the authenticated V2 API;
- automatic OpenCode updates disabled by Order-owned configuration.

Order may also set `OPENCODE_PURE=1` and `OPENCODE_DISABLE_EXTERNAL_SKILLS=1` as defense in depth, but v1 correctness does not depend on those flags unless the pinned certification proves their exact effect.

The bound OpenCode foreground `serve` always composes the V2 API with its embedded Web UI and exposes no CLI/environment switch to disable only that UI. Order therefore does not invent a proxy, network namespace, patched binary, or compatibility layer merely to remove those static routes. The security boundary is the existing private random loopback listener plus the rule that no Order HTTP/browser surface exposes, forwards, links, or otherwise depends on the provider listener. API calls still require the per-process OpenCode password.

The bound OpenCode build still has a Linux system-config source at `/etc/opencode`, while the foreground `serve` command does not expose the programmatic `system: false` switch. Order therefore fails provider startup/certification when `/etc/opencode` exists rather than reimplementing OpenCode's config parser to guess that it is harmless.

The bound OpenCode build's model-facing `read` tool can discover and inject nested repository `AGENTS.md` files after successful reads. Order therefore enumerates every regular repository `AGENTS.md` reachable in the active snapshot before productive provider use, requires every one to resolve through the project's P1 authority selection/precedence, and includes their exact bytes in the resolved context (and post-signoff signed material closure). A task `changeSurface` may not include those signed instruction files. OpenCode's read-triggered injection is thus only a rendering of already-resolved authority; an unresolvable file blocks invocation.

The provider shell supplies only required runtime basics such as `PATH`, locale and temp values in addition to the private values above. Provider login and guided setup use the same private HOME/XDG/database namespace. Order never reads or edits OpenCode credential rows directly.

Environment/default-chain credentials outside that isolated OpenCode namespace are not part of v1. The productive installer therefore establishes or verifies credentials inside the private namespace rather than importing the user's ambient OpenCode database.

## 4. Session model

Every Order Run begins with a fresh OpenCode session.

A session may continue across ordinary interactive turns only when all are true:

- same Order Run;
- same lifecycle stage;
- same resolved `contextHash`;
- same configured provider/model;
- same effective stage permission profile.

If material authority changes, artifact adoption changes resolved context, permissions materially change, or Order cannot prove the provider session is current, Order replaces the OpenCode session before the next productive turn.

A replacement session receives only current canonical stage context, persisted Order evidence and unresolved questions. The old conversation is evidence, not authority.

Sessions never cross Order Runs, lifecycle stages, work items, or builder/reviewer boundaries. R3, implementation and independent review always start from fresh sessions.

## 5. Exact model binding

Order never relies on OpenCode's default-model fallback.

For every new or replacement session Order creates the session for the exact workspace, calls V2 `switchModel` with the configured provider/model, reads session state back, proves the selected model exactly matches, installs permissions, and only then admits a prompt.

There is one configured Order provider/model in v1. Its exact `providerID` and model `id` come from the canonical persisted Order configuration established by guided setup. `PONTIVUS_ORDER_OPENCODE_MODEL` is not a productive configuration source. Dynamic/per-stage routing is outside v1.

## 6. Permission profiles

Order installs explicit V2 session-scoped permission rules before the first productive prompt. The bound OpenCode build uses ordered last-match-wins rules, so Order installs a deny-first baseline followed only by exact role-specific allows.

Every productive profile begins with:

```text
deny action="*" resource="*"
```

`STAGE` allows `read`, `glob` and `grep` with resource `*`. For each configured canonical reference root `R`, STAGE additionally receives one `external_directory` allow with resource `R/*`. Because the pinned provider wildcard treats `*` as spanning path separators, that one rule covers descendants of that exact root. External reads remain read-only and the pinned OpenCode read implementation skips its nearby-`AGENTS.md` injection path for external-directory targets.

`REVIEWER` allows only target-workspace `read`, `glob` and `grep` with resource `*` and receives no external-directory allow.

`BUILDER` and `REMEDIATOR` allow the same target-workspace read-only actions and add one `edit` allow for each exact literal `ExecutionTask.changeSurface` path. `changeSurface` is a `RepositoryPath[]`, not a glob, so Order does not translate Bun.Glob semantics into OpenCode permission semantics. They receive no external-directory allow.

All unlisted capabilities remain denied, including shell/execute, external-directory access outside the exact STAGE reference-root rules, skills, subagents, web and schedule operations. `write` and the bound OpenCode build's multi-file `patch` use OpenCode's canonical `edit` permission action; certification proves every patch source/destination resource is included in the permission assertion before mutation. Order never uses `ask` as a hidden human-interaction path.

The format-repair turn uses a deny-all profile with zero tools.

Pre-signoff **provider/agent-proposed** canonical artifact mutation remains exclusively Order's proposal/adoption boundary. The governed Markdown workbench's explicit direct-human Save is a separate daemon-owned mutation ingress defined by `GW-DOC-MARKDOWN-WORKBENCH-V1`; it grants no additional OpenCode edit permission and never lets provider conversation mutate authority directly. The STAGE prompt includes the exact configured reference-root paths in a separately labeled non-authoritative read-only section so the model can deliberately inspect them; Order does not preload their bytes into resolved canonical context. Readable reference-root bytes are evidence/context only and do not become Order/project authority without the normal governed artifact/adoption path. Post-signoff model mutation is limited to exact signed `changeSurface` paths. Destructive Git, commit, push, merge, deployment and external-directory mutation are not provider capabilities in v1.

Capability certification proves the deny-first rule, exact-path edit allows, multi-resource patch authorization, exact STAGE reference-root external-directory allows, and denied external access for all post-signoff roles before Order permits productive use.

## 7. Prompt admission and serialization

Order serializes productive prompts: at most one Order prompt is in flight per OpenCode session.

Every productive provider turn is triggered by an already-persisted Order RunEvent. Order derives one deterministic OpenCode prompt id from `runId + triggering RunEvent id + contextHash`; the derived value must satisfy the pinned V2 `SessionMessage.ID` contract and therefore starts with `msg_`. This OpenCode input id is the admission/correlation identity. Order does not add a second textual turn-marker protocol to the prompt body.

The released V2 `session.prompt` operation is the admission boundary. In the bound OpenCode build the input is durably admitted before advisory execution begins. Reusing the same user-input id for the same Session and input type is idempotent: the first admission wins and later same-id requests reconcile to that durable admission rather than creating another input. Order therefore never creates a new OpenCode prompt id merely because the original HTTP response was lost or uncertain.

Order does not use OpenCode steering/queue features to create concurrent Order decisions in one session.

## 8. Completion and reconciliation

v1 does not subscribe to OpenCode's live event stream and does not use experimental `session.wait` for correctness.

For each serialized productive turn Order:

1. reads `session.get` and records the current `Session.Info.time.idle` boundary, if any;
2. calls `session.prompt` with the deterministic prompt id;
3. polls `session.get` until `time.idle` strictly advances beyond that boundary;
4. reads the advanced projection's `outcome: succeeded | failed | interrupted`;
5. only on `succeeded`, reads `session.context` and retrieves the completed assistant result for canonical semantic parsing.

The bound OpenCode build guarantees a strictly advancing idle boundary for each non-shutdown terminal projection. `session.active` is process-local liveness only and is never completion authority.

Every productive turn has a fixed 3600-second wall-clock bound from admission/reconciliation through terminal projection. At expiry Order calls `session.interrupt`; if terminal success still cannot be proved through the normal idle/outcome/context path, the Run receives `PROVIDER_FAILURE`.

If a `session.prompt` HTTP result is uncertain while the same provider process/session remains available, Order reconciles the durable projection and may repeat only the same deterministic prompt id. It never creates a second id for the same Order turn.

Provider-process loss never authorizes hidden provider resumption. Pre-signoff read-only stage work may replace the session from current canonical context. Every post-signoff `BUILDER`, `REVIEWER` or `REMEDIATOR` provider loss terminates the current Run and enters the bounded operational-action policy in [GW-DOC-CANONICAL-CONTRACTS-V1 §21](13-canonical-contracts.md). A permitted replacement is a new Order Run, fresh D1 checkout and fresh OpenCode session with the same role/trigger identity.

The browser never consumes OpenCode events directly.

## 9. Semantic output

Order does not depend on a legacy OpenCode SDK structured-output feature.

The productive prompt requires the final assistant message to contain only a JSON array of provider-emittable canonical `RunEventPayload` values in [GW-DOC-CANONICAL-CONTRACTS-V1](13-canonical-contracts.md).

Order retrieves the completed assistant message through the released V2 session contract, parses JSON and validates it with the canonical Zod schema. If formatting alone is invalid, Order may perform exactly one tool-disabled format-repair turn whose only job is to re-encode the immediately preceding answer. A second invalid result is `PROVIDER_FAILED`.

A later native schema-output contract may replace this rendering only after a pinned V2 capability audit; Zod validation remains mandatory.

## 10. Stop conditions

The builder stops and reports rather than improvises on material scope expansion, missing/contradictory authority, requirement/design ambiguity, new architecture decisions, unapproved migration/public-contract change, unavailable required verification, or unrelated defect.

## 11. Remediation

A semantic remediation is a new `REMEDIATOR` Order Run and therefore a fresh OpenCode session and fresh P5-D1 baseline checkout.

Its `triggerEventId` identifies the exact repairable validation/review failure. Order replays the failure's candidate patch evidence into the fresh checkout and verifies the reconstructed candidate hash/changed paths before provider invocation. The remediator receives the same approved task, exact failure evidence and an instruction to correct only that proven failure.

Semantic repair remains bounded by [GW-DOC-VALIDATION-STANDARD-V1](06-validation-standard.md). Provider/transport/coordinator recovery is operational and uses the separate bounded action-key policy in [GW-DOC-CANONICAL-CONTRACTS-V1 §21](13-canonical-contracts.md).

## 12. Provider credentials

Order exposes only:

```text
order provider login <provider>
```

This executes exactly `opencode --standalone auth login <provider>` inside the same private Order provider HOME/XDG/database namespace. The bound OpenCode build's `--standalone` prevents the auth CLI from attaching to or autostarting OpenCode's managed background service; the command-scoped standalone server is owned by the auth CLI and exits with it. The login process is the one v1 external-process exception to bounded captured stdout/stderr because pinned key/form/code authentication explicitly requires an interactive stdin/stdout TTY. Order passes through the operator terminal, supplies the same explicit provider environment, does not parse login output as semantic evidence, and does not duplicate credential storage.

A productive Run fails preflight if the configured provider/model cannot be authenticated and resolved exactly.

## 13. Upgrade tolerance

An OpenCode upgrade is never transparent.

Before changing the pinned server/client version, Order re-verifies V2 authenticated server-info readiness/version, session create/get/prompt/context, deterministic prompt-id admission/idempotency, monotonic `Session.Info.time.idle`/outcome completion semantics, final context retrieval, foreground-`serve` restart behavior, exact model switch/read-back, session permission enforcement, interrupt, auth namespace and final message retrieval.

OpenCode-specific shapes stay in the imperative shell and never enter Order's domain model.
