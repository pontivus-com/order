## 1. Purpose

This document governs the complete Order 0.6.0 design campaign from prerequisite investigation through an adversarially reviewable implementation plan.

The campaign is intentionally concern-driven rather than screen-driven or implementation-driven. Its purpose is to make omissions visible and to ensure that every material product concern has an explicit investigation start, an explicit factual end, a functional-design disposition, a technical-design disposition and final implementation-plan coverage.

The campaign progression is:

```text
G0 — Phase 0 factual/governance baseline established
  |
  v
PHASE 1 / R1
complete concern inventory + evidence-first concern investigations
  |
  | G1/G2: coverage proven; every investigation factually closed
  v
PHASE 2A / R2
complete 0.6.0 functional requirements / functional design
  |
  | G3: all concerns functionally closed + horizontal integration PASS
  v
PHASE 2B / DESIGN
complete technical solution design / P4-P6 consequences
  |
  | G4: all functional obligations technically realized
  v
PHASE 3 / PLAN
final executable implementation plan
  |
  | G5: complete P1->P7 traceability, no orphan task or uncovered requirement
  v
PHASE 4 / R3
adversarial readiness review
  |
  | G6: READY_FOR_SIGNOFF
  v
explicit sign-off / implementation authority
```

Actual implementation is outside this campaign plan. It begins only after the canonical PLAN and R3 package has been explicitly signed off.

## 5. Coverage model

The campaign uses two independent completeness proofs.

### 5.1 Concern coverage

Every material product/design concern must appear in the concern register in §6.

The concern register is derived from current P2/P3 authority, not from the current UI navigation alone. Before C01 begins, Phase 1 must prove that the register covers all current stable functional requirement families and all user-visible workflow surfaces.

If a missing concern is discovered later, it is added to the register with a new stable `Cxx` identifier before analysis continues.

### 5.2 Requirement-to-concern coverage

Phase 1 must establish a coverage ledger:

```text
stable P2/P3 requirement / concern
    -> one or more Cxx concerns
    -> investigation evidence
    -> R2 disposition
    -> DESIGN realization
    -> PLAN task coverage
```

No P3 requirement may remain unmapped. A concern may cover multiple requirements; a requirement may legitimately span concerns, but one concern must be marked primary owner for campaign tracking.

## 7. Concern investigation protocol

Every concern uses the same explicit START -> investigation -> END protocol.

### 7.1 START record

Before evidence collection for a concern begins, add a START record to the concern log in this document:

```text
CONCERN START: Cxx — <name>

Start baseline:
- exact repository commit:
- date:
- current phase: R1

Canonical owners:
- ...

Requirement families:
- ...

Upstream intent:
- ...

Known downstream consumers:
- ...

Incoming cross-concern findings:
- ...

In scope:
- ...

Explicitly out of scope:
- ...

Questions to close:
1. What is factually true now?
2. Is current authority complete and internally consistent for this concern?
3. What user/product problem must 0.6.0 resolve?
4. Which adjacent concerns can invalidate this concern's closure?
```

A concern is then changed from `NOT_STARTED` to `IN_REVIEW`.

### 7.2 Mandatory R1 analysis dimensions

Each concern investigation must close:

1. **Intent** — current P2/product reason and user outcome.
2. **Authority** — canonical owner(s), stable requirement identities and applicable higher rules.
3. **Current behavior** — what current implementation/runtime actually does.
4. **Information ownership** — source facts, producer -> carrier -> consumer chain and mutation owner.
5. **Interaction model** — what the operator can observe and do in every material condition.
6. **State/transition closure** — applicable lifecycle, Run, material, proposal, approval, task and provider conditions.
7. **Negative behavior** — prohibited states/actions and failure semantics.
8. **Recovery** — blocker, retry, stale, cancellation and return-to-owner behavior.
9. **Cross-concern interfaces** — assumptions imported from or exported to other Cxx concerns.
10. **Certification state** — what current tests/evidence prove and what remains unproven.

Current code/tests are evidence below authority. An implementation pattern is never promoted into desired product behavior merely because it exists.

### 7.3 END record

A concern investigation cannot stop informally. It ends with:

```text
CONCERN END: Cxx — <name>

End baseline:
- exact repository commit:
- date:

R1 verdict:
VERIFIED | GAP_FOUND | BLOCKED

Facts established:
- ...

Findings:
- Cxx-F01 ...
- ...

Cross-concern findings emitted:
- X-Cxx-Cyy-01 ...
- ...

Incoming findings resolved:
- ...

Canonical owners implicated:
- ...

Open product decisions for R2:
- NONE | ...

Open factual questions:
- NONE | ...

R1 disposition:
FACTS_CLOSED | GAP_FOUND | BLOCKED

Revalidation trigger:
- ...
```

`VERIFIED` means the factual model is closed; it does **not** mean no 0.6.0 functional change is needed.

No concern reaches R2 while it has an unresolved factual question that could materially change the functional decision.

## 8. Finding and dependency discipline

### 8.1 Stable finding identities

Use:

- `Cxx-Fnn` — finding owned by one concern;
- `X-Cxx-Cyy-nn` — finding discovered in Cxx but requiring disposition in Cyy;
- `G-Fnn` — genuinely campaign-wide foundational finding.

A finding is recorded once at its primary owner and referenced elsewhere.

### 8.2 Cross-concern rule

When C06 exposes a problem in C11, C06 records `X-C06-C11-nn`; C06 does not redesign Approval while still investigating Research.

The C11 START record must list that incoming finding. C11 cannot close until it has explicitly disposed it.

### 8.3 Foundational defect rule

If an investigation exposes a Phase 0-class problem—ambiguous canonical ownership, broken reference lineage, shadow authority, impossible lifecycle topology, or another foundation defect—the active concern becomes `BLOCKED`.

The defect is remediated at its canonical owner through a separately governed WorkItem. After that remediation lands, all concerns whose evidence/authority depended on the changed foundation enter `REVALIDATION`.

## 10. Phase 2A — R2 functional requirements / functional design

### 10.1 Per-concern functional closure

R2 processes the same C01-C20 register.

For each concern, R2 records:

- current authority disposition: `REFERENCE | DELTA | LOCAL` as required by `change-v2`;
- required 0.6.0 user-visible/observable behavior;
- information hierarchy and interaction obligations where applicable;
- state/action/transition/failure/recovery behavior;
- explicit exclusions and non-goals;
- acceptance criteria;
- dependencies on other concerns;
- any permanent P2/P3 owner that must be amended.

A concern reaches `FUNCTIONAL_CLOSED` only when an implementer/technical designer would not need to invent product behavior for that concern.

### 10.2 Functional-design ownership

Normative functional decisions belong in `requirements.md` and the appropriate permanent P2/P3 canonical owner.

This campaign plan records status and references only. It must not become the only place where a product rule exists.

### 10.3 G3 — functional-design gate

G3 requires:

- C01-C22 all `FUNCTIONAL_CLOSED`;
- all R1 findings disposed;
- all cross-concern functional dependencies resolved;
- one complete end-to-end user-flow walkthrough from creation through terminal result;
- all return/recovery paths included;
- complete P2 -> P3 coverage;
- no contradictory current-attention, lifecycle, material, approval, provider or settings rule;
- a horizontal functional integration audit returns PASS.

If G3 fails, affected concerns return to R2 or R1 as appropriate.

## 11. Phase 2B — DESIGN technical solution design

### 11.1 Per-concern technical closure

DESIGN consumes only functionally closed concerns and determines, as applicable:

- canonical semantic owner;
- pure/core derivation vs daemon/shell/UI effect ownership;
- data/control flow;
- contract and schema consequences;
- persistence/transport consequences;
- provider integration consequences;
- existing capabilities to reuse;
- behavior/owners to delete or replace;
- minimum architecture-preserving decomposition;
- failure/rollback behavior;
- permanent verification sensor ownership.

The design must preserve FCIS, SoC, DRY/canonical ownership, strict typing, no-OOP/no-DTO posture and minimum sufficient change.

A concern reaches `TECHNICAL_CLOSED` only when no material architectural choice is delegated to implementation.

### 11.2 Authority amendments

Any P4/P5/P6 change is made at its existing canonical owner. The design records stable IDs and exact semantic-version pins where the package requires a fixed snapshot.

No concern-local duplicate contract/model is permitted for convenience.

### 11.3 G4 — technical-design gate

G4 requires:

- every functional requirement has an explicit technical realization;
- C01-C22 all applicable technical columns are `TECHNICAL_CLOSED`;
- no duplicated semantic owner or transport/persistence/UI shadow shape is introduced;
- complete producer -> carrier -> consumer paths are specified for changed semantics;
- failure/recovery and negative behavior have technical owners;
- permanent verification consequences are defined;
- horizontal technical integration audit returns PASS.

## 12. Phase 3 — PLAN final implementation plan

### 12.1 Plan construction

Only after G4 may the canonical `implementation-plan.md` be finalized.

Every P7 task must provide:

- objective;
- dependencies;
- exact scope;
- explicit exclusions;
- acceptance references;
- expected semantic change surface;
- required gates;
- exact authority references;
- concern IDs covered.

### 12.2 Bidirectional coverage proof

Before PLAN can close, prove both directions:

```text
every required design obligation -> at least one P7 task
every P7 task -> one justified upstream design/requirement obligation
```

A task without upstream justification is scope creep.

A design/requirement without a task is incomplete implementation planning.

### 12.3 G5 — implementation-plan gate

G5 requires:

- all applicable concerns are `PLAN_COVERED`;
- the complete task dependency graph is executable;
- task scopes do not overlap through duplicate semantic ownership;
- the union of task scopes covers the designed change surface;
- exclusions are explicit;
- the gate union covers all required architecture/core/daemon/shell/UI/browser/integration verification;
- the plan contains one valid canonical `order-tasks` block;
- no implementation worker must choose between material design alternatives.

## 13. Phase 4 — R3 readiness and campaign closure

R3 is an adversarial review pass and treats R1/R2/DESIGN/PLAN as untrusted. It does not assume a separate human or worker; separation is by governed stage and evaluation posture, not personnel.

### G6 — readiness gate

G6 passes only with `READY_FOR_SIGNOFF`.

R3 must specifically challenge:

- concern-register completeness;
- whether any concern was closed without a START/END record;
- unresolved incoming cross-concern findings;
- P2 -> P3 -> P4/P5/P6 -> P7 traceability;
- authority/version lineage;
- minimum-change discipline;
- missing negative/failure/recovery coverage;
- implementation ambiguity;
- stale R1 evidence caused by later repository changes.

After G6 and explicit sign-off, this campaign document's status becomes `READY_FOR_IMPLEMENTATION`. Actual execution remains governed by the signed P7 tasks and normal Order execution/validation lifecycle.

## 14. Horizontal integration audits

Individual concern closure is necessary but insufficient.

Three horizontal audits are mandatory.

### H1 — post-R1 factual integration

Before G2:

- prove adjacent concern assumptions agree;
- prove all cross-concern findings have owners;
- identify facts whose evidence changed during later concern reviews;
- revalidate early concerns where necessary.

### H2 — post-R2 functional integration

Before G3, walk the complete product:

```text
install/readiness
-> queue
-> create/source
-> R1
-> R2
-> DESIGN
-> PLAN
-> R3
-> Approval
-> Execution
-> Complete
```

Also walk every valid upstream return, stale-authority path, blocker/retry/resume path, source-change path, provider failure path and settings-readiness recovery.

### H3 — post-DESIGN technical integration

Before G4:

- one owner per semantic concept;
- complete producer/carrier/consumer agreement;
- no DTO/shadow representation;
- no browser-owned business policy;
- no duplicate persistence/transport authority;
- no effect leakage into functional core;
- complete failure/recovery ownership;
- verification at the correct boundary.
